Architecture
The public static app POSTs JSON to /functions/v1/usage-summary. The Edge
Function handles OPTIONS/CORS, validates a maximum 4096 UTF-8 bytes, strips
private/unneeded fields, and calls the private accept_usage transaction.
Postgres stores a durable submission ID and the accepted payload. Duplicate
retries acknowledge the original row before rate limiting. Different content
with the same ID is rejected. Failed inserts cannot mark a submission accepted.
No browser database SDK, service key, user login, or hosted visit database is needed.
The existing endpoint setting permits a staged cutover.

Account and automation authentication
- Owner: use Continue with GitHub at https://supabase.com/dashboard/sign-in with
  your existing GitHub account. Keep its two-factor authentication enabled.
  This signs YOU into the Supabase dashboard; it does not authenticate GitHub jobs.
- Agent access: connect the Supabase integration under your account, granting
  access to this project. If using a local CLI/MCP token instead, create a
  separate scoped Supabase personal access token limited to this project and
  the operations needed. Keep credentials in the connection or local environment.
- GitHub deployments (when added): use a separate project-scoped Supabase PAT
  stored as the Actions secret SUPABASE_ACCESS_TOKEN. GitHub's GITHUB_TOKEN is
  not a Supabase credential. Edge Function deployment needs Edge Functions
  read/write; add only the permissions needed for other deployment operations.
  Supabase documents Project Settings, API Keys and API Key Secrets read access
  for CLI link. Database migrations via db push may separately require the
  database password; a scoped PAT does not restrict direct password-based SQL.
- Probe: NO Supabase access token, service_role key or database password is
  supplied to this job. It only needs the project URL. It calls the public
  aggregate endpoint, which performs a database read using the Edge Function's
  own server-side credentials.
- Application backend and monthly report: the current implementation uses the
  server-only service_role key described below. This is distinct from a PAT.
  It is not used for account login or for the GitHub probe.

Supabase recommends scoped PATs for agents and CI. The convenient browser flow
of supabase login creates a classic, account-wide token. For scoped access,
set SUPABASE_ACCESS_TOKEN in the local environment or use a credential manager
rather than using the browser login command below. Do not share one token across
the agent and CI: separate tokens can be revoked independently.

Database activity probe
The Supabase database probe workflow runs at 02:17, 10:17 and 19:17 UTC, adding
an independently random 0-90 second delay on each scheduled run. Thus intervals
vary around 8, 9 and 7 hours. Manual runs skip the delay. This small jitter avoids
spending long GitHub runner periods asleep. GitHub itself can delay scheduled runs.
The request is GET /functions/v1/usage-summary?stats=1, which executes the existing
read-only usage_stats SQL function. The bare health endpoint is deliberately not
used: it does not prove database access. No synthetic submissions, timestamp
updates or writes are performed, and no aggregate values are logged by the probe.

To activate after deploying the Edge Function:
1. In GitHub Settings -> Secrets and variables -> Actions, set the existing
   repository secret SUPABASE_URL to https://YOUR_PROJECT_REF.supabase.co.
2. Keep repository VARIABLE MWH_SUPABASE_PROBE_ENABLED=false during setup.
3. Merge the workflow to main and run Supabase database probe manually once.
   Manual runs bypass the schedule switch. Expect: Database read succeeded.
   After a successful run, set MWH_SUPABASE_PROBE_ENABLED=true. A failed query
   produces a failed Actions run and should be fixed before enabling scheduling.
4. Check scheduled runs periodically. GitHub can disable schedules in public
   repositories after 60 days without repository activity; probing alone does
   not commit anything. The existing monthly dataset commits normally supply
   repository activity, but this should be checked if refreshes stop.

This is a best-effort activity/availability check, not an uptime guarantee.
Supabase describes Free project pausing after insufficient activity over seven
days and says a few database requests daily are typically sufficient. Only paid
projects are exempt from automatic inactivity pausing. A paused project must be
resumed in the dashboard; this workflow cannot resume it automatically.

Site register email (independent of Supabase)
Update UNESCO Data now produces a separate email after a successful validated
commit and push, including unchanged refreshes. It compares the pre-refresh
canonical catalogue with the committed result by site ID. It reports added,
newly retired, reactivated, changed and unexpectedly removed entries, separating
roots from components. Formatting and generation metadata are ignored. The
email lists up to 40 entries per category; the workflow artifact includes the
complete JSON change list and text report for 90 days. Git remains the permanent
record. Changes are to this application's register, not necessarily new UNESCO
inscriptions or official delistings. The message confirms a pushed catalogue,
not successful completion of a separate Pages deployment.
It uses the same SMTP secrets, sends to pekka@data.co.za, and does not require
MWH_MONTHLY_REPORT_ENABLED or Supabase. Configure all refresh alert secrets,
merge the workflow to main, then verify one scheduled or manual successful run.
Manual refresh runs also send a report; no additional cron job is needed.

Recovery and rollback
For an endpoint rollback, restore the previous endpoint setting. Keep Supabase
rows for audit and avoid resubmitting accepted summaries to both backends.
Disable MWH_MONTHLY_REPORT_ENABLED to stop scheduled email.
For dataset rollback, restore BOTH current outputs and their raw source from
the same ingestion commit or tag, validate, and publish in a new commit.
Do not reset or force-push main.
